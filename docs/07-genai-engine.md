# 07 — The GenAI engine

## What the model is asked to do

Given one localised failing path and the catalogue, choose one transformation
and its parameters. That is the entire output contract:

```json
{"transform": "balanced_mux_tree",
 "params": {"lhs": "alu_c"},
 "reason": "alu_c selects among 16 values with a 16-deep priority chain on op, and every code of op is covered, so the chain is equivalent to a depth-4 tree."}
```

or, when nothing applies:

```json
{"transform": null, "params": {}, "reason": "..."}
```

The model never emits RTL. `genrtl/transforms.py` performs the rewrite. See
[04](04-transform-library.md) for why that decision carries most of the safety
argument.

## What the model is given

`genrtl/proposer.py:build_prompt()` assembles, for one path:

- **objective** — the clock to close, its period, and the hard side constraints
- **the failing path** — startpoint, endpoint, launch and capture clocks, slack,
  arrival, required, logic depth
- **the diagnosis** — `logic_depth`, `single_dominant_stage`, `moderate_depth`
  or `load_or_fanout`, computed from the delay profile
- **delay attributed per RTL module**, as JSON
- **the heaviest stages** on the path, in picoseconds, with pin names
- **the localised RTL slice**, 50–120 numbered lines
- **the protected module list**, with the reason each one is protected
- **the transformation catalogue**, with parameter schemas
- **the sites the structural matcher already found**, with the rationale for
  each
- **the history** of what has been tried and what happened to it
- **the SDC**

Everything in that list is derived from tool output. Nothing is estimated.

## Why the matcher runs first

The structural matcher finds every catalogued transformation whose precondition
actually holds on this path, and those sites go into the prompt. The model is
choosing among verified-applicable options rather than guessing at what might
apply.

Its answer is then **bound back to a detected site**: the named transform must
have a site on this path, and the parameters are validated against that site's
parameters rather than trusted. A transform name that matches no site is
rejected with a specific message:

```
balanced_mux_tree does not match any site on this path;
the structural precondition does not hold
```

The model still adds value in the space that remains: which of several
applicable transforms to try given the delay profile, which cut point to
pipeline at, how many copies to duplicate into, and — through the history block
— when to stop retrying something that keeps getting rejected.

## Backends

Selected by `--llm` or `GENRTL_LLM`.

| Backend | Requires | Notes |
|---|---|---|
| `heuristic` | nothing | default; deterministic ranker |
| `anthropic` | `pip install anthropic`, `ANTHROPIC_API_KEY` | `GENRTL_LLM_MODEL` to pick the model |
| `openai` | `pip install openai`, `OPENAI_API_KEY` | |
| `ollama` | a local Ollama server | `GENRTL_OLLAMA_URL`, stdlib HTTP only |

If a backend fails to construct — package missing, no key — the engine falls
back to the heuristic rather than aborting the run. If a call fails mid-run, the
same fallback applies and the error is recorded in that iteration's record.

## The heuristic backend

Not a stub. It ranks the same candidate sites the model would see, using:

- the transform's own estimated depth reduction, computed from the structure it
  matched (a 16-deep chain becoming 4 deep scores higher than a 4-term adder
  chain becoming 2 deep), and
- an applicability weight per STA diagnosis.

The weights encode which failure mode each transformation actually addresses:

| Diagnosis | Transforms offered |
|---|---|
| `logic_depth` | tree balancing, restructuring, pipelining, factoring, FSM re-encode, retime |
| `moderate_depth` | the same, more evenly weighted |
| `single_dominant_stage` | duplication first, then FSM re-encode, factoring |
| `load_or_fanout` | duplication, factoring |

A weight of zero means "does not address this failure mode" and the transform is
not offered at all. Duplicating a register does nothing for a path that is
simply too deep.

This means the loop's results are **reproducible without an LLM**, which matters
for a benchmark: the numbers in [08](08-metrics-and-results.md) can be
regenerated by anyone with the toolchain and no API access.

## Free-form patches

The brief also describes the model returning a unified diff directly. That path
exists in the design — every gate downstream is diff-agnostic and would catch a
bad patch — but it is not the default, and the reason is worth stating plainly:
in the constrained mode the only thing a wrong answer costs is one rejected
iteration, whereas in free-form mode a wrong answer that happens to pass all
gates is a silent functional change. The gates are strong, but "the model can
only pick from a list of proven-correct rewrites" is a stronger argument than
"the model wrote something and the checker liked it".

## Cost

One call per iteration, with a prompt of roughly 2–4 K tokens and a reply under
200. A 16-iteration run is well under 100 K tokens. The expensive part of the
loop is not the model — it is synthesis, STA and the SAT solver.
